02通用约定

请求头

GET /repos/{owner}/{repo} HTTP/1.1
Host: api.github.com
Accept: application/vnd.github+json
Authorization: Bearer <token>
X-GitHub-Api-Version: 2026-03-10
User-Agent: my-app/1.0
  • 仅 HTTPS（TLS 1.2+），请求/响应均为 JSON（二进制下载除外）。
  • X-GitHub-Api-Version 固定 API 行为，避免升级被 breaking change 影响；省略用最新版。
  • 时间戳一律 ISO 8601 / UTC。

分页

方式说明
页码式（主流）?page=2&per_page=100，默认 30，上限 100
Link 响应头rel="next" —— 是否还有下一页的唯一可靠依据
游标式（部分）?cursor=...&per_page=...，按响应体 after/before 传递

条件请求

  • 响应含 ETag/Last-Modified；带 If-None-Match/If-Modified-Since 重发，未变化返回 304，不消耗速率额度。

错误模型

{
  "message": "Validation Failed",
  "documentation_url": "https://docs.github.com/...",
  "errors": [{ "resource": "Issue", "field": "title", "code": "missing_field" }]
}
状态码含义
301 / 302资源迁移（跟随 Location；不应自动转 PUT/POST）
304条件请求命中缓存
401凭证缺失 / 无效
403权限不足 / 二级限速（看 Retry-After）
404不存在或无权限（GitHub 不区分二者）
409冲突（如 commit 已存在）
422字段校验失败（errors[] 给细节）
429速率超限
5xx服务端故障，指数退避重试

03认证体系

方式适用要点
PAT（fine-grained）个人脚本、小工具细粒度授权 + 过期时间，推荐
PAT（classic）兼容旧场景repo 等粗粒度 scope
GitHub App组织级 / 生产（推荐）JWT → installation token，权限最细、额度最高
OAuth App代表单个用户授权码流程；无浏览器用 Device Flow
GITHUB_TOKENActions 工作流内自动注入轮换，权限按声明收窄
GitHub App 流程：
1. 私钥签 JWT（iss=App ID，exp ≤ 10min，RS256）
2. GET  /app/installations                     → installation_id
3. POST /app/installations/{id}/access_tokens  → 1 小时有效 token
4. Authorization: Bearer <installation_token>
Token 只走请求头，禁止拼 URL；401 先查过期与权限范围。

04速率限制

维度限制
REST（已认证）5,000 次/小时（App installation token 更高）
REST（未认证）60 次/小时（按 IP）
Search API30 次/分钟（认证）/ 10 次/分钟（未认证）

  • 二级限制：短时高频、并发超标 → 403/429 + Retry-After（秒），必须退避。

06GraphQL API v4

  • 单端点 https://api.github.com/graphql，仅 POST；无日期版本化，变更经 schema 弃用标注发布。
  • 强类型 schema + introspection（在线工具：GraphQL Explorer / Inspector）。
  • Relay 游标分页：first/after/before/last + pageInfo { hasNextPage endCursor }。
  • 核心优势：一次请求拉取嵌套资源，替代 REST 多次串行请求。
query {
  repository(owner: "github", name: "docs") {
    stargazerCount
    issues(first: 10, states: OPEN, orderBy: {field: CREATED_AT, direction: DESC}) {
      pageInfo { endCursor hasNextPage }
      nodes { number title author { login } }
    }
  }
}
场景推荐
CRUD、下载资产、触发 ActionREST（语义直白、SDK 成熟）
仪表盘/报表聚合、深层数据一次取齐GraphQL
实时事件Webhooks（两者都不适合轮询）

07Webhooks 与事件体系

在仓库/组织设置（或 API）注册回调 URL，GitHub 对订阅事件 POST JSON。当前 50+ 种事件：push、issues、pull_request、release、workflow_run…

X-GitHub-Event: pull_request       ← 事件类型
X-GitHub-Delivery: 72d3162e-...    ← 投递唯一 ID（幂等去重键）
X-Hub-Signature-256: sha256=...    ← HMAC-SHA256(secret, raw_body)
# 1. 校验签名（常数时间比较，防伪造）
expected = "sha256=" + hmac.new(secret, raw_body, hashlib.sha256).hexdigest()
hmac.compare_digest(expected, header)
# 2. 幂等：X-GitHub-Delivery 去重（GitHub 会重投）
# 3. 快速响应：10 秒内返回 2xx；重活转队列异步处理
  • 首次创建 webhook 会收到 ping 事件，务必正常响应。
  • 投递失败指数退避重试，可在仓库后台手动 redeliver。

09最佳实践 Checklist

  • ☑ 用 Webhooks 替代轮询；必须轮询时用条件请求（304 不计费）
  • ☑ 分页一律跟 Link 头，不要自己数条数
  • ☑ 429 / 二级限速 → 读 Retry-After 指数退避；422 → 打印 errors[]
  • ☑ 请求头固定 X-GitHub-Api-Version，升级前测试环境跑回归
  • ☑ 生产集成用 GitHub App 而非个人 PAT
  • ☑ 大批量数据走 GraphQL 聚合或 /git 底层对象
  • ☑ Token 只走请求头与密钥管理，不进日志、不进代码库

Part III重点分类端点详解

Actions 与 Git database：参数、请求体、典型流程与选型建议

III·1Actions API

路径省略前缀 https://api.github.com/repos/{owner}/{repo}；组织级路径另行标注。写操作返回 204 即成功。fine-grained PAT 需 Actions: read/write。

Workflow 定义

GET/actions/workflows列出全部工作流（id、path、state）
GET/actions/workflows/{id或文件名}单个工作流（可直接用 .yml 文件名）
PUT/actions/workflows/{id}/enable /disable启用 / 禁用
GET/actions/workflows/{id}/usage计费时长（毫秒）
POST/actions/workflows/{id}/dispatches手动触发，body {"ref":"main","inputs":{}}

Workflow Runs

GET/actions/runs列出 runs；筛选：actor branch event status conclusion created head_sha
GET/actions/runs/{run_id}单次 run 详情
GET/actions/runs/{run_id}/attempts/{n}第 n 次尝试（重跑后）
POST/actions/runs/{run_id}/cancel取消
POST/actions/runs/{run_id}/rerun重跑（可带 enable_debug_logging）
POST/actions/runs/{run_id}/rerun-failed-jobs只重跑失败 job
DELETE/actions/runs/{run_id}删除 run
GET/actions/runs/{run_id}/logs下载日志 → 302 zip 临时地址（60s 有效）
DELETE/actions/runs/{run_id}/logs删除日志
GET/actions/runs/{run_id}/timing运行时长
POST/actions/runs/{run_id}/pending_deployments/{id}/review审批环境部署，body {"state":"approved"}

Jobs 与 Artifacts

GET/actions/runs/{run_id}/jobsrun 下全部 job（含每 step 的 conclusion）
GET/actions/jobs/{job_id}单 job 详情
GET/actions/jobs/{job_id}/logsjob 日志（302 → 纯文本）
GET/actions/runs/{run_id}/artifacts某 run 的产物
GET/actions/artifacts仓库全部产物
GET/actions/artifacts/{id}/zip下载 zip（302 → 签名临时地址，需跟随）
DELETE/actions/artifacts/{id}删除；默认保留 90 天

Secrets / Variables / Runners / 权限

GET/actions/secrets/public-key取 key_id + public_key，用于 libsodium sealed box 加密
PUT/actions/secrets/{name}写入 secret（只写不读），body encrypted_value + key_id
PUT/actions/variables/{name}非加密变量 body {"value":"..."}
POST/actions/runners/registration-token获取自托管 runner 注册 token
GET PUT/actions/permissions/workflow默认 GITHUB_TOKEN 权限（read_all / write_all / 按 scope）
GET PUT/actions/oidc/customization/subOIDC token 的 sub 声明自定义（keyless 场景必配）
GET DELETE/actions/cache缓存列表 / 删除（限额 10GB，满了要先清）

III·2Git database API

操作底层 Git 对象。只建对象不更新 ref，GitHub 不感知（不出现在 PR/UI 关联里）。fine-grained PAT 需 Contents: write。
GET/git/blobs/{sha}blob 内容（base64），可 Accept: raw
POST/git/blobsbody {"content":"...","encoding":"utf-8|base64"} → 新 blob sha
GET/git/commits/{sha}commit 对象（区别于 /commits：不含 diff）
GET/git/trees/{sha}?recursive=1树（>10 万条目会 truncated:true）
POST/git/treesbody 含 base_tree + tree[]（path/mode/type/sha）
GET/git/ref/heads/main读引用；通配用 /git/matching-refs/{prefix}
POST/git/refs新建分支：{"ref":"refs/heads/x","sha":"..."}
PATCH/git/refs/{ref}移动 ref = 提交生效：{"sha":"新commit","force":false}
DELETE/git/refs/{ref}删分支；受保护分支返回 422
POST/git/tagsannotated tag（lightweight tag 直接打 ref）

无工作区提交六步流程

1. GET  /git/ref/heads/main                  → 当前 commit sha
2. GET  /git/commits/{sha}                   → base tree sha
3. POST /git/blobs                           → 新内容 → blob sha
4. POST /git/trees  (base_tree=旧tree)       → 新 tree sha
5. POST /git/commits (tree, parents=[旧sha]) → 新 commit sha
6. PATCH /git/refs/heads/main  {"sha":新}    → 分支指向新 commit，完成
  • 并发防护：第 6 步若 ref 已被推进返回 409/422，重走流程即可（乐观锁语义）。
  • 批量改多文件：第 4 步一个 tree 放多条 entry，一次 commit 全部生效。
